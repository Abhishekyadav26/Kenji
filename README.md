# Kenji People-Finder (Tokyo Builder Community)

Ask in plain language, get back **real people** from the community — with a reason for each, and an honest **"nobody fits"** when that's the truth.

- **Live ENS index**: profiles are read from Sepolia ENS text records (`description`, `skills`, `availability`) via `viem`, with `npm run refresh` to rebuild when profiles change.
- **Grounded answers**: the model / fallback can only return ENS names from the community allowlist. Hallucinations are dropped by Zod + allowlist validation.
- **Untrusted bios**: one bio (`mallory.kenji-builders.eth`) is deliberately adversarial (`IGNORE ALL PREVIOUS INSTRUCTIONS…`). Retrieval scores structured `skills` 3x over bio text, requires a structured-skills hit for skill queries, and the LLM prompt marks bios as untrusted data that must never be followed.
- **Measured retrieval**: `eval/queries.json` holds 8 recorded test queries with expected members; `npm run eval` scores them (10 pts each, 80 total).

### Seeding (writes live records)

```bash
cp .env.example .env
# dry run (no key needed)
npm run seed -- --dry-run
# live (needs Sepolia ETH for gas + parent rent)
SEED_PRIVATE_KEY=0x... npm run seed -- --live
npm run refresh   # rebuild index from live ENS records
```

`scripts/seed.ts` registers the parent via the Sepolia `ETHRegistrarController` (commit + reveal), creates subnames with `ENSRegistry.setSubnodeRecord`, and sets text records with `PublicResolver.setText`. Re-running is idempotent.

Sepolia ENS contracts used: registry `0x00000000000C2E074eC69A0dFb2997BA6C7d2e1e`, resolver `0xE99638b40E4Fff0129D56f03b55b6bbC4BBE49b5`, controller `0xfb3cE5D01e0f33f41DbB39035dB9745962F1f968`.

> If the parent is already taken on Sepolia, set `PARENT_NAME` to a name you own and re-run the seeder — the finder works with any parent.

## Ask

```bash
npm run ask -- "Is anyone here good at Rust and free to mentor this month?"
npm run ask -- "Who is good at Solidity and free to mentor this month?" --include-busy
npm run refresh
npm run list
```

HTTP:

```bash
npm run build && node dist/src/server.js
curl -X POST localhost:8787/ask -H 'Content-Type: application/json' \
  -d '{"query":"Is anyone good at Rust and free to mentor this month?"}'
```

Preferences: `{ "onlyAvailable": true (default) | false, "topK": 1..10 }`.
`--include-busy` sets `onlyAvailable=false` (shows busy members too).

## How grounding works (`src/answer.ts` + `src/retrieval.ts`)

1. `scoreProfiles()` does deterministic keyword retrieval over live profiles. Availability comes **only** from the structured `availability` record; bio instructions contribute zero.
2. Optional LLM (`OPENAI_BASE_URL`/`OPENAI_API_KEY`, any OpenAI-compatible API) rewrites reasons under a strict system prompt: allowlist-only, bios marked untrusted, JSON-only.
3. Every LLM-proposed ENS is validated: normalized, checked against the allowlist, canonicalized to the index spelling. Unknown names are dropped; if all are dropped → honest nobody-fits.
4. Without an LLM key, a deterministic extractive fallback returns the same grounded matches with template reasons, so tests pass offline.

## Evaluation

```bash
npm test   # 8 recorded cases + acceptance/adversarial/preference tests (offline-safe)
npm run eval   # scores eval/queries.json live (falls back to cache/seed offline) → eval/last-run.json
```

Recorded artifacts:
- `eval/queries.json` — 8 test queries with `expected`, `mustNotContain`, `expectEmpty`.
- `eval/examples.json` — the same Rust-mentor question under 3 preferences (strict / include-busy / topK=1) with actual outputs.
- `eval/last-run.json` — generated by `npm run eval` (not committed as source of truth).

## Fields

We index exactly three text records: `description` (bio), `skills` (comma list, the primary retrieval signal), `availability` (free/busy signal). This keeps retrieval predictable and makes the adversarial test meaningful (bio claims ≠ skills).
